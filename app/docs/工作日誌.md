- **設備買入**:比照其他類型,存檔整張重開(`ledger.save_voucher`)。借設備科目(依類別查
  `FIXED_ASSET_ACCOUNTS`,全額成本)/貸現金銀行存款(淨額)/貸政府補助收入(補助款,
  >0 才加,重用 9 宮格「其他收益」那輪已經建好的 `4881-02` 科目)。`fixed_asset` 加
  `payment_account` 欄位(datalist,同這輪其他表單)。
- **折舊**:開 `/assets` 頁時系統順便把還沒記過的月份補上。新增 `ledger.save_voucher_if_new`
  ——跟既有 `save_voucher`(整張重開)不同,這個是「缺的月份才補,已經記過的不動」,
  因為折舊是累加的歷史記錄不是一份會被覆蓋的當前狀態。`Q.sync_depreciation_vouchers()`
  沿用既有 `asset_dep_base()` 平均法公式,不重寫計算方式。只補到「這個月」,不像
  `_asset_dep_rows()` 那樣把未來幾年排程都算出來。
- 資產處分或刪除資產卡時,`delete_voucher_for("asset_depreciation", aid)` 一次清掉該資產
  所有月份的折舊分錄(這個函式本來就是刪光符合 source_type+source_id 的列,不分
  voucher_no,天生適合)。
- 總帳頁這兩類傳票(`asset_acquire`/`asset_depreciation`)**不給勾選刪除**——折舊一台
  資產對到很多張月份傳票,勾一張沒辦法只刪那個月,要管理回 `/assets` 頁做。

**測試方式**:直接 POST 測整套生命週期(新增資產驗證借貸平衡 → 開 `/assets` 頁驗證折舊
傳票數量/金額對、重複開頁不會產生重複月份 → 編輯改成本驗證買入傳票重開不是疊加 →

## 2026-10-01(續)訂單匯入(Google 表單 / Excel)—— 後端 + 畫面完成

家易希望訂單可以用 Google 表單或 Excel 匯入,不用每次手動再打一次。先跟使用者討論定案
設計方向(表單給客人自己填、CSV + xlsx 都支援、保守的客戶配對、預覽/確認才真的寫入、用
時間戳記防重複匯入——完整理由見本檔上方「待處理 / 決策」區塊),畫了一版 Design canvas
示意圖給使用者看過、確認方向對,才動工。

**固定欄位規格**(表頭文字要完全對,是跟家易設計 Google 表單時的依據):
`時間戳記`(或 `Timestamp`,Google 表單內建自動產生)、`客戶姓名`、`客戶電話`(必填,比對
客戶用)、`收件地址`、`付款方式`、`備註`。除此之外,**任何欄名剛好等於某個「在售」商品的
品名或 SKU,就自動當成那個商品的數量欄**——這樣表單只要設計成「每個商品一個數量下拉/
核取方塊」,商品品項完全不會有打字誤植問題(客人沒有打字的機會),比對失敗的風險只剩電話
打錯這一種,比原本設想的「品名自由文字 + 模糊比對」安全很多。

**新檔 `app/order_import.py`**:只管「解析檔案 + 比對」,不碰資料庫寫入——
- `parse_file(filename, content)`:依副檔名分流,`.csv` 用內建 `csv` 模組(嘗試
  `utf-8-sig`/`cp950`/`utf-8` 解碼,對應 Google 表單跟 Excel 兩種常見編碼來源);`.xlsx`
  用新加的 `openpyxl`(`requirements.txt` 新增 `openpyxl==3.1.5`)。
- `match_rows(headers, raw_rows, pay_methods)`:逐列判斷狀態——
  - **防呆細節**:電話欄如果被 Excel 當數字存掉(開頭的 0 不見,例如 `912345678`),
    `_phone_from_cell()` 會自動補回去;比對時另外用 `normalize_phone()` 去掉空格/破折號
    再比,格式不同不會誤判成新客戶。
  - 時間戳記缺 / 電話缺 / 一個商品都沒勾 → `error`,附原因文字,不會被匯入。
  - 時間戳記對應的 `gform:<原始時間戳記>` 已經存在某張訂單的 `source_ref` → `duplicate`,
    自動略過(家易整份表單重新匯出上傳也不會變成兩筆)。
  - 電話完全比對到既有客戶 → `ok`。比對不到 → `new_customer`,交給預覽畫面讓家易決定
    「建立新客戶」還是「其實是某個既有客戶」——**絕不自動模糊比對姓名**,同名但電話對不上
    一律當不同人處理,寧可多問一次。
  - 表頭裡對不到任何商品的欄位,整批收集成 `unmatched_headers`,在預覽畫面最上面用一條
    警示整批列出來(不是每列都重複講),家易看得到「表單欄位跟商品目錄兜不起來了」。

**`main.py` 新路由(訂單管理區塊,`next_order_no`/`sync_order_stock`/`_post_order_ledger`
定義之後)**:
- `GET /orders/import`:上傳畫面,選銷售管道 + 選檔案。
- `POST /orders/import/preview`:呼叫 `OI.parse_file` + `OI.match_rows`,把「可匯入/新客戶」
  列跟「有問題/已匯入過」列分開,渲染預覽畫面。整批解析結果(含每列明細)塞進一個隱藏欄位
  `rows_json`(走 Jinja 自動跳脫,不是自己手刻的,沒有 XSS 風險)——**沿用 `ledger_confirm.html`
  那套「不額外存檔、靠表單隱藏欄位把整批資料帶到下一步」的既有模式**,沒有另外加資料表或暫存檔。
- `POST /orders/import/confirm`:解析 `rows_json` + 每列的 `resolve_i`(`new` 或某個
  `customer_id`)+ `skip_i`(打勾就整列跳過)。`new` 的話先建客戶(`segment` 固定給
  `零售`,`primary_channel_id` 設成這批匯入選的管道),單價查 `price_list` 的方式跟
  `order_create()` 手動新增那條路完全一樣;真正寫入訂單/明細後,**呼叫同一組
  `sync_order_stock()` + `_post_order_ledger()`**,出庫紀錄跟總帳分錄不會漏記或算兩套邏輯。
  完成後導回 `/orders?imported=N`。

**畫面**:新增 `orders_import.html`(上傳,跟手動新增訂單用同一組「手動新增 / 匯入」切頁

## 2026-10-02:全鏈路毛利分析(問題 2)

先用示意圖(Artifact,`https://claude.ai/artifact/BuNXrXJYbJ5qyF6K3wez89`)跟使用者講清楚
兩件事再動工:①現有儀表板/總帳/正式三表/獲利報表/各產品線損益**全部都是公司角度**,從
公司付給小農的採購款算起,小農自己的田間管理/採收成本不會出現在公司帳上,而且這點**不會
變**;②「全鏈路毛利分析」是**另開的新頁面**,把已經付的採購款往前拆解估算,不是多算一筆
錢,毛利總額不變。問清楚兩個開工前的問題:①估算值要不要留歷史——**要,照產季分開存**,
之後回頭看某一季用的是「那一季當時填的數字」,不會被後來改的值影響,新一季預設帶上一季的
數字當起點;②四條產品線一次做齊,不是先做一條。用 Plan Mode 設計(先派 Explore 分析
`/pricing`/`pricing_param`/`product_line_pnl` 現有結構,再寫計畫,一樣存在
`elegant-swinging-firefly.md`)。

**資料設計**:新表 `chain_cost_param(season, pg_name, supply_cost)`——估算值存「整季
總額」,不是「單價 × 數量」。原因:龍眼乾/龍眼肉/蜂蜜賣的是加工後成品,成品計價單位
(包/罐)跟鮮果投入量不是 1:1,要換算成「這批成品耗用了多少台斤鮮果」需要另一組轉換率,
問題會滾雪球——改成整季總額直接跟公司真實採購款比較最單純,比照 `/pricing` 既有
`lab_harvest`(元/年,不是元/單位)的做法。**不重用** `pricing_param`——那張表是單一
key-value、不分產季,跟這裡「依產季留歷史」的模型不一樣。

**中途修正(重要,記下來避免以後走回頭路)**:第一版欄位叫 `field_mgmt`(田間管理)+
`harvest_labor`(採收工資),隱含假設「龍眼乾/龍眼肉是公司自己拿鮮果加工出來的,田間管理
只對鮮果線有意義」,還畫了一版「鮮果→龍眼乾→龍眼肉」鏈式轉換的示意圖
(`https://claude.ai/artifact/A9dcjB9Ae5h5qbp6im2W9k`)。使用者推翻這個假設,原因有兩層:
①龍眼乾/龍眼肉也可能是**直接跟供應端買現成加工品**,不一定是公司自己加工(小農自己做的
加工品一樣不用報稅,他可以直接賣成品給郡碩);②更關鍵的是,**郡碩沒有自有果園,但老闆
家易自己有果園**——郡碩其實是跟家易買鮮果或加工品,不是(只)跟外部小農/合作社買。同一條
產品線每季供應方式都可能不一樣,系統沒辦法、也不需要判斷是哪一種。**最終定案**:拿掉鏈式
轉換,四條產品線結構維持完全一樣、各自獨立,欄位合併成一個不預設情境的
`supply_cost`(供應端生產成本估算),文案統一用「供應端」取代「小農端」。

**核心函式**(`queries.py`):`chain_cost_params(season)` 查某一季 4 條產品線的估算值,
查不到當季資料時**不補 0**,往回找最近一個已經填過的產季當預設顯示值(`ORDER BY season
DESC LIMIT 1`)——使用者沒按儲存以前,這只是顯示用的預設,不會真的寫進這一季。
`chain_margin(season)` 組合真實數字(**直接重用 `product_line_pnl(season)` 回傳的
`revenue`/`qty`/`direct_material`/`ship_cost`**,刻意不碰 `profit`/`contribution`/
`shared_alloc`——那些含共同費用分攤跟折舊,混進來會讓「供應端估算淨利」失去意義)+ 估算
數字,算出 `supply_profit`(供應端估算淨利 = 採購款 − 估算成本)、`company_profit`(公司端,
簡化版只扣採購款跟運費,不分攤共同費用)、`chain_margin_pct`(驗證:
`company_profit+supply_profit` 要等於用這個百分比算出來的全鏈路毛利金額,證明只是拆分
不是多算)。

**路由**(`main.py`):`/chain-margin` GET/POST。**刻意不借用 `_season_ctx`**(那個會連帶
帶出儀表板那套「依產季/依西曆年」切換,這頁用不到,供應端估算本來就是跟著產季抓的,沒有
西曆年版本)——自己寫一個單純的 `?season=` 讀取。

**模板**(`chain_margin.html`,新檔):比照 `/pricing` 的卡片分組寫法,每條產品線一張卡:
上半唯讀顯示真實數字(營收/採購款/運費/公司端毛利),中段一個可編輯輸入框(供應端生產
成本估算,帶入預設值時上面會註明「目前帶的是哪一季的估算值」),下半唯讀顯示算出來的
供應端估算淨利/全鏈路毛利率——供應端淨利算出負的會標紅、加一句提醒(估算可能偏高,或
採購價真的壓低)。頁首白話提醒這是估算、不影響總帳/報表,也說明四條線不分加工方式。
導覽加在「看數字」群組、「定價試算」後面。

**`/pricing` 這輪沒有動**:那頁鮮果→龍眼乾→龍眼肉的鏈式成本模型(`ratio_fresh_dry`/
`ratio_dry_meat` 等)跟「公司自己種/自己加工」的假設矛盾這件事,工作日誌前面已經記過
(2026-10-01 公司 vs 小農商業模式澄清那條),使用者這輪確認**先不改**,維持獨立待辦。

## 2026-10-02(續)PythonAnywhere 卡死,改走 Render——完整除錯紀錄 + 決策

延續上一則,實際跑完 PythonAnywhere 部署流程(建虛擬環境時先踩到一個 `mkvirtualenv` +
`_posixsubprocess` 找不到的環境汙染問題,開新 Bash console 重建就解掉,跟下面主線問題
無關),一路做到 Reload + 開網址測試——**網站打開後一直轉圈圈,進不去**。

**除錯過程**:
1. 先懷疑是密碼邏輯(`GY_PASSWORD` middleware)的問題,但瀏覽器**連帳密輸入框都沒跳出來**
   ——代表問題在更前面,程式可能根本沒有正常處理請求。
2. Error log 整份是空的。懷疑是使用者家裡網路卡,請他在 PythonAnywhere 自己的 Bash
   console 跑 `curl -v https://chihsuanwang.pythonanywhere.com/` 直接從內部測——**一樣
   卡住沒反應**,排除「是使用者家裡網路慢」這個可能性,確認是伺服器端真的卡死。
3. 改看 **Server log**(跟 Error log 不同的另一份,記開機過程)——這份有東西,挖出關鍵
   證據:uWSGI 有正常啟動、app 有正常 import(`WSGI app 0 ready in 0~3 seconds`,沒有
   任何錯誤訊息),但每一個實際進來的請求(`GET /`、`GET /favicon.ico`)都在幾分鐘後被
   **HARAKIRI** 機制強制砍掉重開("worker ... died, killed by signal 9")——uWSGI
   自己的逾時保護,代表 worker 收到請求後就卡死不回應,不是程式出錯噴例外。
   更關鍵的是:log 裡還留著 **2026-09-09**(更早之前使用者第一次嘗試部署)的紀錄,
   當時就是一模一樣的 HARAKIRI 卡死模式——證實**這不是今天哪個設定步驟做錯,從最早
   第一次嘗試就是這樣**,問題在更根本的地方。
4. 用 `WebSearch` 查證(不是憑記憶猜),查到兩個直接對應的結果:
   - 別人在 PythonAnywhere 上用一模一樣的組合(`a2wsgi` + FastAPI)也回報過一樣的
     症狀(請求卡 59~60 秒被 HARAKIRI 砍掉)。
   - **PythonAnywhere 的免費/標準 Web App 只吃 WSGI,FastAPI 是 ASGI 框架,官方並不
     正式支援**(有一個 alpha 階段的實驗性 ASGI 功能,要另外聯絡 support 參加測試,
     不是標準流程能用的東西)。

**結論**:這是 PythonAnywhere 平台本身的限制,`a2wsgi` 把 ASGI 硬橋接成 WSGI 這條路線
在 PythonAnywhere 的 uWSGI 上**不穩定會卡死**,不是哪一步設定錯——之前推薦走
PythonAnywhere 這個方向本身就不適合這個系統,算是重新評估後發現的錯誤建議。

**連帶查了一輪 2026 年現在的免費方案現況**(也是用 WebSearch 查證,不是猜):
- **Render** 免費版原生支援 ASGI(FastAPI 沒問題),但免費版硬碟是**暫存的**——服務
  睡眠 / 重啟,SQLite 檔案會被清空,不適合需要資料留著的情境。
- **Fly.io**(原本文件裡寫的長期備案)**已經在 2024 年取消新帳號的免費方案**,現在
  只有 2 小時或 7 天試用,之後要綁卡、最低大概每月 $5 美金——不再是「免費」選項了,

## 2026-10-02(續)真的 bug:「確認分錄」畫面按「確認存檔」完全沒反應

使用者在正式網站上試打一筆進貨(中寮果農合作社)準備明天介紹,到「確認分錄」畫面按
「確認存檔」整個沒反應——網址沒變、也沒跳出任何錯誤。

**排查**:先看 `ledger_confirm.html` + `/purchases/confirm` 路由本身,表單結構跟伺服器
邏輯都很單純,看不出問題。請使用者開瀏覽器 **F12 → Network** 看有沒有送出請求——**完全
沒有新請求**,代表問題卡在瀏覽器端、根本沒送出去。改看 **Console**,抓到關鍵訊息:
`An invalid form control with name='invoice_no' is not focusable.`

**根因**:「發票號碼」欄位(`id="invoiceNo"`)原本就帶 `required`,只在憑證類型不是
「發票」時用外層 `<div id="invoiceNoField" hidden>` 把它**藏起來**,但 JS 的
`toggleInvoiceNo()` 只切換 `hidden`,**沒有跟著切換 `required`**。瀏覽器送出表單前的
原生驗證,發現一個必填欄位空著想跳提示框,但那個欄位被藏起來沒辦法 focus,結果**整個
送出動作被瀏覽器自己擋下來、完全不送出 request**,畫面上卻看不出任何提示——這正是
`ledger_confirm.html` 被「進貨」跟「營運費用」兩個畫面共用,憑證類型只要**不選「發票」**
(例如選「農民收據」或留白)就會 100% 重現,是從這個模板一開始寫出來就帶著的 bug,只是
之前的測試剛好都沒踩到「憑證類型留空/選其他」又真的按下存檔這個組合。

**修法**:`toggleInvoiceNo()` 裡讓 `invoiceNo.required` 跟著 `hidden` 一起切換——
欄位藏起來的時候順便拿掉 `required`,顯示的時候(選「發票」)才要求必填。一行邏輯改動,
`ledger_confirm.html` 只有一份,進貨跟營運費用兩個畫面共用同一次修正。

**驗證**:本機開伺服器,直接 POST 一筆進貨到確認畫面,檢查渲染出來的 HTML 確認
`toggleInvoiceNo()` 有正確把 `invoiceNo.required` 跟 `hidden` 綁在一起、而且頁面載入時
就會呼叫一次(不是只有 `change` 事件才生效,一開始空白的狀態也要處理對)。瀏覽器端的
實際點擊行為沒辦法用 curl 驗證(這是純瀏覽器端的 HTML5 表單驗證行為),等推上 Render
後請使用者在原本重現的畫面直接重試確認。測完的假資料用 `seed.py --empty` 清掉,
本機恢復空白狀態。

**總帳明細排序 bug**:使用者說直覺應該是純日期排序、最新在最上面,但畫面看起來像是

用真正的日期欄位當主要排序依據,同一張傳票的借貸兩列(voucher_no 相同、entry_date 也
一定相同)還是會排在一起不會拆散。驗證過改完之後不同類別的傳票會依時間正確交錯排列。

## 2026-10-02(續)訂單「收款狀態/出貨狀態」可以在沒填金額/日期的情況下直接選「已收款/

**改法(比原本討論的「拿掉下拉選項」更簡單安全)**:沒有去動下拉選單的選項內容(避免
